# ADR: Wails build output — what is in, and what is out

**Status:** accepted (product 1.1.0, contract v1.1.0); **amended for Wails v3** (contract v1.2.0). **Fixes:** nothing — new coverage (Providers 21 → 22).

## Context

Wails builds a desktop app from Go plus a web frontend. `wails build` runs the
frontend bundler, embeds the result into the Go binary, and writes the app to
`build/bin/`. The expensive caches behind those builds (`GOCACHE`,
`GOMODCACHE`, `node_modules`) already have providers; only the per-project
output was unreported. The question was whether it belongs, and — the harder
half — which part of `build/` may be offered.

## Decision — what is in

| id | generation | marker | paths | why this safety |
|---|---|---|---|---|
| `wails` | v2 | `wails.json` | `build/bin/`, `frontend/dist/` | both are generated by `wails build`; `frontend/dist` is bundler output → `safe`, `build/bin` costs a full rebuild → `caution` |
| `wails` | v3 | `go.mod` with `github.com/wailsapp/wails/v3` **and** (`build/config.yml` or `Taskfile.yml` invoking `wails3`) | `bin/`, `frontend/dist/`, root `dist/` when a root `package.json` exists | `bin/` is the compiler/package output → `caution`; frontend bundles → `safe` |

The marker sits at the project root, so this cannot be a `TreeRule`: a rule
only sees the matched directory's parent, and `build/bin` / `frontend/dist`
sit two levels below the marker. The scanner walks each root for markers
(pruning `.git`, `node_modules`, `target`, `vendor`, `Pods`, `.dart_tool`,
`.svelte-kit`, `build`, `dist`) and then inspects the fixed child paths.

### Why v3 needs its own marker

Wails v3's official project structure and build system use `Taskfile.yml` +
`build/config.yml`; there is no `wails.json` in a fresh v3 project. The v3
migration page still shows a `wails.json` snippet, which is stale relative to
those two references. Requiring **both** the Go dependency and the v3 build
config avoids treating an unrelated Go module that merely imports Wails as an
application. If a migrating project keeps both markers, v3 wins so the wrong
(`build/bin`) path is not offered.

Root `dist/` is only reported for a v3 project with a root `package.json`:
that is the custom frontend layout, and the guard keeps an unrelated `dist/`
from being offered. The template-default `frontend/dist/` is reported when it
exists.

## Decision — what is out, and why

- **The whole `build/` directory.** It holds committed assets —
  `build/config.yml`, `appicon.png`, the platform `Info.plist`/manifest
  templates — not just generated output. Deleting it removes files the user is expected to edit and
  commit. This applies to both generations.
- **Other paths under `build/`** (e.g. `build/darwin`, `build/windows`):
  templates and per-platform config, same argument. Only `build/bin` (v2) is
  the compiler's output.
- **`frontend/node_modules`** stays under the `node_modules` provider — it is
  shared across frameworks, not Wails-specific.
- **`GOCACHE` / `GOMODCACHE`** stay under `go_cache`, resolved through `go env`
  so a custom location is honoured.
- **A marker that ships inside a dependency** (`node_modules/**`) is not a
  project we own; the marker walk prunes dependency trees.
- **`.task/`** is Task's own cache and is small; it is not worth a row.

## Consequences

- One provider id on the wire (`wails`, prefix `wa`) and one card in the
  dashboard; no command or event changed.
- A Wails project whose output lives elsewhere (custom output path, or a
  `build/bin` removed by the toolchain) simply reports nothing — absence stays
  normal.
- Wails v3 output is now visible on machines that never had `wails.json`;
  the resource count can grow without a provider-count change.
